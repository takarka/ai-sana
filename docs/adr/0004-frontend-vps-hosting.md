# Публичный сайт хостится на self-managed VPS (Docker + nginx), не на Vercel/CDN

[04-landing-migration.md, §7 L-2](../plan/04-landing-migration.md#7-открытые-вопросы)
оставлял открытым выбор между двумя контурами хостинга SSR-сервера `landing`:
тот же контур, что backend (self-managed сервер), или отдельный
PaaS/edge-контур (Vercel и аналоги). Решение принято владельцем проекта
10.09.2026: **self-managed VPS**, тем же паттерном, что предполагался для
backend (реверс-прокси перед Node-процессом — см. 04-landing-migration.md,
таблицу §2, строку «Хостинг SSR»). Развёрнутый план — [05-vps-deployment.md](../plan/05-vps-deployment.md).

## Что зафиксировано

| Позиция | Значение |
|---|---|
| Контур | Self-managed Linux VPS (Ubuntu LTS), не PaaS/edge (Vercel, Netlify и т.п.) |
| Контейнеризация | Docker + Docker Compose — SSR-процесс `landing` собирается в образ и запускается контейнером |
| Реверс-прокси / TLS | nginx на хосте, сертификаты — Let's Encrypt (`certbot`), автопродление |
| Доставка | GitHub Actions: сборка образа → push в GHCR → SSH-деплой на VPS (`docker compose pull && up -d`) |
| Секреты | Только в GitHub Actions Secrets (host, ключ доступа, при необходимости — переменные окружения контейнера); в репозитории и в документации — не хранятся, конкретные хосты/учётные данные в плане не публикуются |
| Охват этого решения | Только `apps/landing` (публичный сайт). Хостинг `craft-web` (кабинет) и backend API — вне рамок, каждый получит собственное решение при переходе к соответствующему этапу |

## Почему не Vercel/edge-CDN

- Проект уже эксплуатирует self-managed паттерн для локальной разработки
  (`platform/docker-compose.yml` — Postgres/Redis, 01-bootstrap-platform.md) и,
  по всей видимости, будет эксплуатировать его для backend — держать два разных
  эксплуатационных паттерна (PaaS для лендинга, VPS для API) увеличивает
  когнitivную нагрузку на небольшую команду без явной выгоды: у лендинга нет
  большого географически распределённого трафика, который оправдывал бы
  edge-рендеринг.
- [PD-01](../tz/02-tz-nfr-i-priemka.md) требует размещения персональных данных
  граждан РК на территории РК; демо-форма лендинга (FR-WEB-02) собирает ФИО,
  школу, e-mail, телефон — как только очередь-заглушка (04-landing-migration.md,
  «Что этот этап НЕ делает») превращается в реальное хранилище, это ПДн.
  Большинство глобальных PaaS/edge-провайдеров не дают гарантии размещения
  данных строго в РК; self-managed VPS у РК-провайдера снимает вопрос по
  конструкции.
- Стоимость и предсказуемость: self-managed VPS — тот же класс расходов и
  эксплуатационных навыков, что уже нужен для backend; не вводит зависимость от
  ещё одного внешнего провайдера с отдельным биллингом и SLA.

## Почему не откладываем решение

Как и в случае с [ADR-0002](0002-frontend-stack-angular-tailwind.md) и
[ADR-0003](0003-landing-eighth-version-to-angular.md), вопрос блокировал шаг 6
плана 04 (cutover — «Домен/прокси переключается на SSR-сервер landing»):
без выбора контура нельзя было детализировать пайплайн доставки. Выбор
конкретного РК-провайдера и конкретного VPS остаётся отдельным, более узким
вопросом (см. [ТЗ Q-2](../tz/02-tz-nfr-i-priemka.md#14-риски-и-открытые-вопросы))
и не блокирует этот ADR: контур («self-managed VPS») не зависит от того, какой
именно провайдер выбран.
