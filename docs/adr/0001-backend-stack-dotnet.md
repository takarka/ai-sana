# Бэкенд платформы — .NET 10 (ASP.NET Core), модульный монолит

ТЗ оставляло выбор между .NET и Node.js + NestJS открытым (вопрос Q-7,
[часть 2](../tz/02-tz-nfr-i-priemka.md)). Выбираем **.NET 10 (LTS)** и
**ASP.NET Core** с архитектурой модульного монолита и вертикальными срезами —
состав стека и обоснование каждой позиции описаны в
[плане инициализации, раздел 2.2](../plan/01-bootstrap-platform.md). Решение
принято владельцем проекта 10.09.2026; с этого момента альтернатива на Node.js
не рассматривается, а `platform/back` создаётся сразу под .NET.

## Что именно зафиксировано

| Позиция | Значение |
|---|---|
| Платформа | .NET 10 (LTS) |
| Веб-слой | ASP.NET Core, Minimal APIs с `MapGroup` по модулям |
| Архитектура | Модульный монолит, вертикальные срезы внутри модулей, без mediator |
| Данные | EF Core 10 + Npgsql, PostgreSQL 16+, схема на модуль |
| Реальное время | SignalR + Redis backplane |
| Фоновые задачи и кэш | Hangfire (или Quartz.NET), Redis |
| Оркестрация и наблюдаемость | .NET Aspire (AppHost + ServiceDefaults), OpenTelemetry |
| Тесты | xUnit + `WebApplicationFactory` + Testcontainers + NetArchTest |
| Версии пакетов | Central Package Management (`Directory.Packages.props`) |

## Почему не Node.js + NestJS

- Нагрузочный профиль (60 000 учеников, 5 000 одновременно) закрывается и тем,
  и другим стеком — решение определяется не производительностью.
- Учебные данные сильно связаны (прогресс → попытка → оценка → отчёт), и
  ключевое требование FR-CORE-01 (изоляция школ) надёжнее закрывается
  глобальными фильтрами EF Core плюс RLS в Postgres, чем ручной фильтрацией.
- .NET Aspire даёт локальный запуск «одной командой» и OpenTelemetry,
  health-checks и политики устойчивости из коробки — это прямо закрывает
  NFR-OBS-01…03 без сборки собственной обвязки.
- Один язык на бэкенде и в тестах против связки TypeScript-рантайма и отдельных
  инструментов миграций; для команды 12–16 человек это меньше разнородности.

Цена решения: кадровый рынок .NET в РК уже, чем Node.js. Это принимается
осознанно — вопрос Q-7 изначально был сформулирован именно про доступность
кадров у заказчика.

## Версия платформы: почему 10, а не 8 из ТЗ

ТЗ называло .NET 8. Поддержка .NET 8 (LTS) заканчивается в ноябре 2026 года —
раньше, чем платформа дойдёт до продуктива. .NET 10 — действующий LTS. .NET 11
не берём: это STS-релиз, для школьной системы с многолетним сроком жизни нужен
LTS. Таблица стека в [части 1 ТЗ](../tz/01-tz-platforma.md) приведена в
соответствие.

## Сверка с официальными скиллами .NET

Стек проверен против официального набора агентских скиллов Microsoft
(`dotnet/skills`, установлены в [`.agents/skills/`](../../.agents/skills/README.md)).
Расхождений с планом не нашлось; уточнения, которые нужно учесть на шаге 0:

- **OpenAPI.** Скилл `dotnet-webapi` прямо запрещает `Swashbuckle.*` на .NET 9+
  и предписывает `Microsoft.AspNetCore.OpenApi` — это и был выбор плана. Оттуда
  же: `TypedResults` вместо `Results` и `AddProblemDetails()` для ошибок.
- **Наблюдаемость.** `configuring-opentelemetry-dotnet` требует
  `OpenTelemetry.Extensions.Hosting` и единый OTLP-экспортёр по
  `OTEL_EXPORTER_OTLP_ENDPOINT` — ровно то, что даёт Aspire ServiceDefaults.
- **Тесты.** `scaffold-dotnet-test-project` предупреждает: `dotnet new xunit`
  выдаёт пакеты xUnit 2; при Central Package Management проект под xUnit v3
  нужно создавать соответствующим шаблоном, а не переписывать версии вручную.
- **Сборка.** `directory-build-organization`: условия по `$(TargetFramework)` в
  `Directory.Build.props` молча не срабатывают для проектов с одним TFM — такие
  условия должны жить в `Directory.Build.targets`.
- **ИИ-шлюз.** `technology-selection` рекомендует `Microsoft.Extensions.AI`
  (`IChatClient`, регистрация провайдера через `AddChatClient`) как слой
  абстракции над провайдером LLM. Это готовый ответ на FR-AI-12: смена внешнего
  провайдера на self-hosted модель не затрагивает прикладной код. План
  библиотеку не называл — фиксируем здесь.
