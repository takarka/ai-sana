# План работ: деплой `apps/landing` на VPS (Docker + nginx)

**Задача.** Развернуть SSR-сервер публичного сайта `apps/landing`
(04-landing-migration.md) на self-managed Linux VPS: контейнеризация,
реверс-прокси с TLS, CI/CD-пайплайн для автоматической доставки, staging-контур
для проверки перед cutover.

**Смежные документы.**
[04-landing-migration.md](04-landing-migration.md) — шаги 0–4 этого плана уже
выполнены в `main`: `platform/front/apps/landing` существует, собирается
(`npx nx build landing` из `platform/front/`, `defaultConfiguration: production`)
и отдаёт SSR через `apps/landing/src/server.ts`. Ниже — контур, на котором этот
процесс работает в проде; конкретные пути и команды ниже сверены с реальным
кодом, а не предполагаются. [01-bootstrap-platform.md](01-bootstrap-platform.md) —
паттерн `docker-compose.yml` для локальной разработки, переиспользуемый здесь
для прод-оркестрации. [ADR-0004](../adr/0004-frontend-vps-hosting.md) — решение
о контуре (self-managed VPS, не PaaS/edge), закрывает открытый вопрос L-2 плана
04. [ТЗ, NFR-REL-01…03, NFR-OBS-01…03, PD-01](../tz/02-tz-nfr-i-priemka.md) —
требования к доступности, наблюдаемости и размещению данных, на которые
опирается этот план.

**Результат этапа.** `apps/landing` собирается в Docker-образ через CI,
разворачивается на VPS за nginx с TLS-сертификатом, автоматически
пересобирается и передеплоивается по пушу в ветку развёртывания; staging-контур
на том же или втором VPS позволяет проверить релиз до переключения домена
(шаг 6 плана 04).

**Что этот этап НЕ делает:** не выбирает конкретного VPS-провайдера
(ТЗ, [Q-2](../tz/02-tz-nfr-i-priemka.md#14-риски-и-открытые-вопросы) — отдельный,
более узкий вопрос, см. §7); не разворачивает `craft-web` (кабинет) и backend
API — у них будет собственный план при переходе к соответствующему этапу; не
описывает конкретные IP-адреса, домены или учётные данные конкретного сервера —
это эксплуатационные секреты, их место в GitHub Actions Secrets или менеджере
секретов, не в репозитории и не в документации.

## 1. Целевая архитектура

```
Интернет
   │  443/tcp (TLS)
   ▼
┌─────────────────────────────── VPS (Ubuntu LTS) ───────────────────────────────┐
│                                                                                  │
│   nginx (хост-процесс)                                                          │
│     ├─ TLS-терминация (Let's Encrypt / certbot, автопродление)                  │
│     ├─ / → reverse_proxy → 127.0.0.1:<PORT_PROD>   (контейнер landing:prod)     │
│     └─ staging.<домен> → 127.0.0.1:<PORT_STAGING>  (контейнер landing:staging)  │
│                                                                                  │
│   docker compose (prod)                                                         │
│     └─ landing:  образ ghcr.io/<org>/landing:<sha>, restart: unless-stopped     │
│                                                                                  │
│   docker compose (staging)                                                      │
│     └─ landing:  образ ghcr.io/<org>/landing:<sha-предыдущего-релиза-на-проверке>│
│                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Прод и staging — два независимых Docker Compose проекта на одном VPS (разные
порты, разные `server_name` в nginx), либо два отдельных VPS, если ресурсов
одного не хватает (решается по факту нагрузки, не блокирует этот план).

## 2. Решения по стеку деплоя

| Позиция | Решение | Почему |
|---|---|---|
| ОС | Ubuntu LTS (24.04 на момент написания) | Самая предсказуемая база для Docker/nginx/certbot, максимум документации и пакетов |
| Контейнеризация | Docker + Docker Compose | Тот же инструмент, что уже в `platform/docker-compose.yml` для локальной разработки (01-bootstrap-platform.md) — не вводим второй способ упаковки |
| Образ | Multi-stage `Dockerfile`, build-контекст — весь Nx-воркспейс `platform/front/` (не `apps/landing/` отдельно: нужны `nx.json`, `tsconfig.base.json`, `libs/shared/*`). Сборка — `node:22` (`platform/front/.nvmrc`), рантайм — `node:22-slim` | Версия Node зафиксирована в `.nvmrc`, не берём произвольный LTS; минимизирует размер образа и поверхность атаки в рантайм-слое |
| Точка входа рантайма | `node server/server.mjs` с рабочей директорией `dist/apps/landing` — путь проверен сборкой (`npx nx build landing` → `dist/apps/landing/{browser,server}/server.mjs`), локали лежат в `browser/ru`, `browser/kk` и `server/ru`, `server/kk` | `server.ts` резолвит `browserDistFolder` относительно `server/`, поэтому оба каталога должны копироваться в образ рядом |
| Реестр образов | GitHub Container Registry (`ghcr.io`) | Уже есть доступ через тот же GitHub-репозиторий и токен CI, не нужен третий провайдер |
| Процесс на хосте | Контейнер, а не systemd-unit с голым `node server.js` | Совпадает по рантайму с CI-сборкой (то же, что тестировалось), упрощает откат — смена тега образа, а не пересборка на хосте |
| Реверс-прокси / TLS | nginx (хост-пакет) + `certbot --nginx` | Стандартная связка, автопродление через systemd-таймер `certbot.timer`, не требует контейнеризации самого nginx |
| Доставка (CI/CD) | GitHub Actions: `build` → `push в ghcr.io` → `ssh deploy` (`docker compose pull && up -d`) | Тот же CI, что уже упоминается в 04-landing-migration.md §4 шаг 5 (`platform-front.yml`); отдельный джоб `deploy`, срабатывающий на пуш в ветку развёртывания (например, `main`) после зелёного `lint,test,build` |
| Секреты деплоя | GitHub Actions Secrets: адрес хоста, приватный SSH-ключ деплой-пользователя (не `root`), путь на сервере | Никогда не в репозитории; деплой-пользователь — отдельный, с правом только на `docker compose` в своей директории (см. §5) |
| Откат | `docker compose pull ghcr.io/<org>/landing:<предыдущий-sha> && up -d` вручную или повторным запуском деплой-джоба на предыдущем коммите | Быстрее пересборки: образ предыдущего релиза уже в реестре |

**Замечание по сборке.** Текущий `production`-билд уже пререндерит 8 статических
маршрутов (главная/MATRIX/BUILDER/PISA × ru/kk) поверх SSR — Angular application
builder включает это по умолчанию для не персонализированных маршрутов. Это
частично закрывает открытый вопрос L-4 плана 04 (SSG вместо SSR для статичных
секций); дальнейшая настройка prerender-конфигурации — задача плана 04, не
этого плана, но контейнеру это ничего не меняет: SSR-процесс всё равно нужен
для маршрутов, не попавших в prerender, и обслуживает уже собранные
пререндеренные файлы как статику.

## 3. Структура на сервере

```
/opt/craft-ai/
├── prod/
│   ├── docker-compose.yml       # сервис landing, образ :latest-prod (тег фиксируется деплоем)
│   └── .env                     # непубличные переменные окружения контейнера (не в git)
├── staging/
│   ├── docker-compose.yml
│   └── .env
└── nginx/
    └── (симлинки/include в /etc/nginx/sites-enabled/, версионируются отдельно
         от приложения — см. §5)
```

`docker-compose.yml` в `prod/` и `staging/` — из репозитория (директория
`platform/front/apps/landing/deploy/` — см. шаг 2 ниже), различается только
`.env` и тегом образа, который проставляет деплой-джоб.

## 4. Пошаговый план

### Шаг 0. Предусловия

- [ ] VPS выбран и выделен заказчиком/DevOps (РК-провайдер — по
      [Q-2 ТЗ](../tz/02-tz-nfr-i-priemka.md#14-риски-и-открытые-вопросы), см. §7).
- [ ] Домен и DNS-доступ для A-записи прод- и staging-поддомена.
- [x] `apps/landing` собирается локально — выполнено в `main`: 04-landing-migration.md
      пройден до шага 4 включительно (контент MATRIX/BUILDER/PISA перенесён,
      SSR и `@angular/localize` работают, доступность проверена).

**DoD:** есть SSH-доступ к пустому VPS с root, есть домен; `cd platform/front &&
npx nx build landing` проходит локально (проверено — production-конфигурация
по умолчанию, вывод в `dist/apps/landing/{browser,server}`).

### Шаг 1. Базовая настройка VPS

- [ ] Создать непривилегированного `deploy`-пользователя с sudo только на
      `docker compose` в `/opt/craft-ai/{prod,staging}` (через `sudoers`-правило
      с явным списком команд, не `NOPASSWD: ALL`).
- [ ] Установить Docker Engine + Docker Compose plugin, добавить `deploy` в
      группу `docker`.
- [ ] Установить nginx, `certbot` и `python3-certbot-nginx`.
- [ ] Настроить `ufw`: разрешить 22 (SSH, желательно с ограничением по
      IP/ключу), 80, 443; всё остальное — закрыто.
- [ ] Отключить вход `root` по паролю в `sshd_config` (`PermitRootLogin
      prohibit-password` или `no`), оставить только вход по ключу.
- [ ] Сгенерировать отдельный SSH-ключ для деплоя (не переиспользовать личные
      ключи инженеров), публичную часть — в `authorized_keys` пользователя
      `deploy`, приватную — в GitHub Actions Secrets.

**DoD:** `ssh deploy@<host>` по ключу работает, `docker run hello-world`
проходит от `deploy`, вход `root` по паролю отключён, `ufw status` показывает
только 22/80/443.

**Если VPS выдан с root-доступом «как есть»** (пароль пришёл в открытом виде —
почтой, чатом и т.п.): первым действием после входа сменить пароль root **и**
сразу выполнить этот шаг (отключить парольный вход, завести `deploy`). Любой
пароль, который прошёл через незашифрованный канал, считается скомпрометированным
независимо от того, был ли он кем-то использован.

### Шаг 2. `Dockerfile` и compose-файлы в репозитории

- [ ] `platform/front/apps/landing/Dockerfile` — multi-stage, **контекст сборки —
      `platform/front/`** (весь Nx-воркспейс, не только `apps/landing/`: нужны
      `nx.json`, `tsconfig.base.json`, `libs/shared/ui`, `libs/shared/ui-tokens`):
      1. `node:22` — `npm ci` (по `package.json`/`package-lock.json` воркспейса),
         `npx nx build landing` (клиентский + серверный бандл, локали `ru`/`kk`);
      2. `node:22-slim` — свежий `npm ci --omit=dev` в этом слое (по тем же
         `package.json`/`package-lock.json`, скопированным отдельно, чтобы не
         тащить в рантайм `@nx/*`, ESLint, Playwright и прочие dev-зависимости
         воркспейса) + копируются `dist/apps/landing/browser` и
         `dist/apps/landing/server` из слоя сборки; `WORKDIR /app/dist/apps/landing`,
         `CMD ["node", "server/server.mjs"]` — путь подтверждён реальной сборкой,
         не предполагается.
- [ ] `platform/front/apps/landing/deploy/docker-compose.yml` — один сервис
      `landing`, `image` без тега (проставляется деплоем), `restart:
      unless-stopped`, `env_file: .env`, порт публикуется только на
      `127.0.0.1:<PORT>` (наружу — через nginx, не напрямую); `PORT` — та же
      переменная окружения, что уже читает `server.ts` (по умолчанию `4000`).
- [ ] `.dockerignore` в `platform/front/` (build-контекст) — исключает
      `node_modules`, `dist`, `.angular/cache`, `coverage`, тесты обоих
      приложений (`craft-web`, `landing`) и `craft-web`/`landing-e2e`, если они
      не нужны в образе.

**DoD:** `docker build -f platform/front/apps/landing/Dockerfile platform/front`
собирает образ локально, `docker run -p 4000:4000 <образ>` отдаёт SSR-страницу
на `localhost:4000` (редирект `/` → `/ru/` по умолчанию, `/kk/` при
`Accept-Language: kk`).

### Шаг 3. nginx и TLS

- [ ] Конфиг `server { server_name <домен>; location / { proxy_pass
      http://127.0.0.1:<PORT_PROD>; ... } }` — с проксированием заголовков
      (`X-Forwarded-For`, `X-Forwarded-Proto`, `Host`) и `gzip`/`brotli` для
      текстовых ответов.
- [ ] Аналогичный `server`-блок для `staging.<домен>` на `PORT_STAGING`.
- [ ] `certbot --nginx -d <домен> -d staging.<домен>` — выпуск и автопродление.
- [ ] HTTP → HTTPS редирект.

**DoD:** `https://staging.<домен>` отдаёт тестовый контейнер (см. шаг 4) с
валидным сертификатом; `curl -I http://<домен>` возвращает 301 на `https`.

### Шаг 4. CI/CD-пайплайн

- [ ] Джоб `deploy` в `.github/workflows/platform-front.yml` (после зелёного
      `lint,test,build` из 04-landing-migration.md §4 шаг 5), с условием на
      ветку: пуш в `main` → деплой на **staging** автоматически; деплой на
      **prod** — вручную (`workflow_dispatch` или approve через GitHub
      Environments с защитой ветки) — переключение прод-домена без ручного
      подтверждения не делаем.
- [ ] Шаги джоба: `docker build` → `docker push ghcr.io/<org>/landing:${{
      github.sha }}` → `ssh deploy@<host> "cd /opt/craft-ai/<env> && sed -i
      's|image:.*|image: ghcr.io/<org>/landing:${{ github.sha }}|' \
      docker-compose.yml && docker compose pull && docker compose up -d"`.
- [ ] GitHub Environments (`staging`, `production`) со своими секретами
      (`DEPLOY_HOST`, `DEPLOY_SSH_KEY`, `DEPLOY_PATH`) — секреты `production`
      доступны только джобу, задеплоенному через `environment: production` с
      required reviewers.

**DoD:** пуш в `main` через 5–10 минут обновляет staging без ручных действий;
прод обновляется только через явный approve; образ каждого релиза остаётся в
`ghcr.io` для отката.

### Шаг 5. Здоровье и наблюдаемость

- [ ] Добавить в `apps/landing/src/server.ts` маршрут `/healthz` (простой 200 OK
      без побочных эффектов, регистрируется до `app.use('/**', ...)`, который
      сейчас перехватывает всё) — на момент написания этого плана в `server.ts`
      такого маршрута нет, это входит в объём данного шага, а не уже сделано.
      Docker healthcheck в compose (`healthcheck:` с `curl`/`wget`) и точка для
      будущего внешнего мониторинга (NFR-OBS-02).
- [ ] Логи контейнера — через `docker compose logs` на первое время;
      подключение к централизованному логированию (NFR-OBS-01) — когда появится
      общий контур для backend, не блокирует этот этап.
- [ ] `logrotate` для nginx access/error логов на хосте (иначе диск VPS
      заполняется без внешнего мониторинга).

**DoD:** `docker inspect --format='{{.State.Health.Status}}'` на контейнере
показывает `healthy`; `/var/log/nginx/*.log` ротируется.

### Шаг 6. Переключение прода (согласовано с шагом 6 плана 04)

- [ ] Staging проверен (см. DoD плана 04, п. 1–6).
- [ ] A-запись основного домена переключается на VPS (если раньше указывала на
      статический хостинг `eighth-version/`).
- [ ] Первый прод-деплой — вручную approve через GitHub Environment `production`.
- [ ] После подтверждения — удаление легаси-версий лендинга из root
      (04-landing-migration.md §4 шаг 6, ADR-0003) — это часть плана 04, не
      данного плана; здесь только фиксируется, что удаление идёт **после**,
      не одновременно с переключением DNS.

**DoD:** публичный домен отдаёт `apps/landing` с прода через nginx/TLS;
`eighth-version/` и более ранние версии ещё не удалены (это следующий пункт по
плану 04) — сначала подтверждается стабильность прод-контура минимум сутки.

## 5. Соглашения

| Что | Правило |
|---|---|
| Секреты | Только в GitHub Actions Secrets / GitHub Environments; ни в `docker-compose.yml`, ни в `.env`, закоммиченных в git (`.env` — в `.gitignore`), ни в этом или любом другом документе репозитория |
| Root-доступ | Не используется для деплоя и CI; только для первичной настройки (шаг 1), после чего парольный вход отключается |
| Теги образов | Всегда `git sha`, никогда `:latest` в проде — иначе откат невозможен без пересборки |
| Прямой доступ к порту приложения | Запрещён — порт публикуется только на `127.0.0.1`, наружу отдаёт только nginx |
| Ветки/коммиты | Тот же Conventional Commits, что в 04-landing-migration.md (`feat(deploy): ...`, `chore(deploy): ...`) |

## 6. Definition of Done этапа

1. `apps/landing` собирается в Docker-образ через CI и публикуется в `ghcr.io`
   с тегом `git sha`.
2. Staging-контур обновляется автоматически при пуше в `main`, доступен по
   HTTPS с валидным сертификатом.
3. Прод-контур обновляется только через явный approve (GitHub Environment
   `production`), доступен по HTTPS на основном домене.
4. Откат — сменой тега образа в `docker-compose.yml` на VPS, без пересборки,
   занимает не более нескольких минут.
5. Root-доступ к VPS не используется в CI/CD; деплой идёт от ограниченного
   пользователя по SSH-ключу.
6. Ни один секрет (пароль, приватный ключ, IP конкретного прод-сервера) не
   закоммичен в репозиторий.

**Оценка трудоёмкости:** 2–4 рабочих дня для одного инженера с опытом
Docker/nginx — большая часть конфигурации переиспользуется как есть между
staging и prod, основное время уходит на первичную настройку VPS и CI-пайплайна.

| Docker-образ, CI/CD с раздельными staging/production Environments | Управляемый, воспроизводимый релизный процесс — предпосылка для NFR-REL-02 (плановые работы только вне учебного времени, с уведомлением) |
| Health-check, логи, `logrotate` | Основа для NFR-OBS-01…02; полный алертинг (NFR-OBS-03) — вне рамок (см. D-5) |

| Явный approve для прод-деплоя, теги образов по `git sha`, откат без пересборки | Снижает время восстановления при регрессии — вклад в NFR-REL-03 (RTO ≤ 2 часа) для контура лендинга |
| Provider-agnostic план, явно не фиксирующий провайдера | Оставляет выбор РК-провайдера открытым для решения по PD-01 и Q-2, не создаёт технологической привязки, которая предвосхищала бы это решение |
